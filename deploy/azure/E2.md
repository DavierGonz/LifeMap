# Entrega 2: preparación local y actualización autorizada de E1

**No ejecutar operaciones Azure hasta autorización del usuario.** Esta fase no
enciende la VM, no usa SSH/SCP, no publica Git ni cambia el servidor. El estado
actual remoto de Jenkins, disco y VM queda pendiente; los JSON E1 son históricos.

## Gates comprobables

Jenkinsfile conserva checkout Git y `pollSCM('H/2 * * * *')`. El job privado
`lifemap-main` en Azure debe usar main confiable; no construir forks arbitrarios
con acceso al socket Docker. El token Kaggle existente permanece en Jenkins;
E2 no vuelve a consultarlo, descargar datos ni entrenar.

Secuencia: aislamiento/salud → builds secuenciales → pytest → hashes de los
modelos y checkpoints → 100 reseñas Yelp por Kafka/consumidor actual → otras
100 de la misma muestra en un **scope CI aislado con la imagen Spark nueva**
→ diez endpoints/interfaz de candidata → promoción. Así se prueba el código
construido, no solo el consumidor anterior. `test_fixture=true` en este scope
marca aislamiento: los textos son Yelp real, no sintéticos; las colecciones
`__e2_test_*` jamás aparecen en API/dashboard de producción.

La selección CI está en dataset_cache/lifemap-e2/ci-smoke-100.json. Reenvíos
posteriores conservan ID y `processed_at`; Kafka entrega de nuevo y ambos
consumidores avanzan offsets, pero Mongo no duplica. La prueba compara las 100
predicciones con los pesos temporales guardados, comprueba inferencia de riesgo,
geometrías/ventanas/alertas y conserva E1 16.944/1.320.594. No interpreta la
muestra dirigida de F4, ni las alertas acumuladas, como prevalencia poblacional.

`DEPLOY_TARGET=validate-only` no promueve; `local` demuestra actualización y
rollback solo locales; `azure` usa la transacción Caddy existente y únicamente
acepta el directorio real `/home/azureuser/LifeMap`. El default del Jenkinsfile
es Azure para el futuro job main autorizado. Los lanzadores de pruebas locales
siempre suministran validate-only/local y no permiten azure.

Para repetir preparación local con el árbol aún sin commit:

```powershell
.\.venv\Scripts\python.exe scripts/jenkins_e2_local.py prepare --snapshot
.\.venv\Scripts\python.exe scripts/jenkins_e2_local.py run --target local
.\.venv\Scripts\python.exe scripts/jenkins_e2_local.py run --target local --fault
```

La preparación hace checkout Git y superpone un tar del árbol auditado en el
job local, documentado como snapshot, no como commit publicado. Con Git limpio
usar `prepare` sin snapshot: checkout exclusivo del commit por bundle. El job
E1 local y las credenciales no se reemplazan. Una falla de pytest debe dejar
FAILURE/JUnit y omitir humo, candidata y promoción. La candidata/containers
efímeros se limpian solo por nombre y label de ese build; no se borran volúmenes.

## Recursos y compatibilidad

Diez servicios/imágenes comprobados linux/amd64: MongoDB 8.0.16; Spark 3.5.8
master/worker; Dask 2025.5.1 scheduler/dos workers; Flask 3.1.3/Gunicorn 23.0.0,
Python 3.10.20; Jenkins 2.568.3/JDK21; Kafka 4.1.2 KRaft; consumidor Spark.
Los conectores Mongo/Kafka son los fijados en las imágenes ya existentes.

| Servicio | Límite MiB | CPU máxima |
| --- | ---: | ---: |
| MongoDB | 768 | 1 |
| Spark master / worker | 1024 / 1536 | 1 / 1 |
| Dask scheduler / dos workers | 384 / 1024 cada uno | 0,5 / 1 cada uno |
| Flask | 256 | 0,5 |
| Jenkins | 768 | 1 |
| Kafka / streaming | 1024 cada uno | 1 cada uno |

Suma: **8.625 GiB**, techos de CPU agregados 9, no reservas simultáneas.
Sobre 4 vCPU/16 GiB: builds secuenciales, Dask/Spark batch o entrenamiento no
concurrentes con la demo. La candidata añade 256 MiB; el consumidor CI añade
1 GiB solo durante su prueba y termina antes de promover. Reservar memoria
para Ubuntu/BuildKit/caché. Detener avance ante OOM/degradación real.

Auditoría local aproximada: Mongo 2,1 GB, Kafka 88 MB, modelos 2,3 MB y
checkpoints <1 MB en el momento de medición. **No enviar 17,85 GB de caché
Kaggle**, scratch ni jenkins_home local. Transferir imágenes API/streaming/Kafka;
reutilizar las seis instancias E1 restantes y Jenkins/Caddy del servidor.
Los locks/volúmenes de los otros proyectos no se usan.

El disco Azure nominal de 128 GiB no demuestra espacio libre. Tras autorizar
encendido/SSH: comprobar `free -h`, `df -h /var/lib/docker`, `docker system df`,
versiones y ocho servicios E1. Exigir **30 GiB libres**, o más si dos copias de
backup+paquete superan esa reserva; no limpiar imágenes/volúmenes para forzarlo.

## Orden de la actualización futura

1. Autorizar encendido/auditoría del servidor. Inspeccionar `lifemap-main`
   mediante su túnel privado; conservar XML/job, historial y credenciales y
   pausarlo antes del primer push E2 para evitar desplegar sobre E1 incompleta.
2. En Azure crear directorio privado de backup con fecha única, guardar
   Caddyfile, `.env`, IDs de imágenes API/streaming si existe y configuración
   Jenkins. No publicar esos archivos. Copiar e2-mongo-transfer.sh al Mongo y
   ejecutar `backup /tmp/lifemap-e2-preupgrade-<fecha>`; conservar el dump
   completo con índices fuera del contenedor. No exporta usuarios/contraseñas.
3. En local terminar productores/CI y, **solo después de autorización**, parar
   streaming y Kafka normalmente. Mongo/API/E1 siguen activos. Ejecutar:

```powershell
.\.venv\Scripts\python.exe scripts/prepare_e2_transfer.py
```

   Se niega a actuar con Git sucio, procesos Kafka/streaming activos o CI activo.
   No los detiene ni reinicia automáticamente. Genera artifacts/e2-transfer-*:
   código de Git + bundle, imágenes, dos modelos versionados, Kafka completo,
   checkpoint production, nueve colecciones E2 con índices y caché CI mínima.
   No copia `.env`, `.secrets`, llaves, usuarios Mongo ni el puntero E1
   `sentiment-active.json`. `manifest.json` y SHA256SUMS comprueban integridad.
   Mantener el snapshot congelado hasta acabar la transferencia inicial; no
   mezclar Kafka de un instante con Mongo/checkpoints de otro.
4. Transferir ese directorio por SSH/SCP usando la llave **solo como identidad**,
   tras autorización. En Ubuntu ejecutar `sha256sum -c SHA256SUMS`. Cargar
   images.tar con `docker load`. No volver a descargar Yelp ni entrenar.
5. Guardar el código E1 y colocar el código E2 revisado; conservar `.env` y
   `.secrets` remotos. Crear solo los volúmenes propios que falten. Kafka debe
   seguir detenido: restaurar Kafka **entero**, incluidos metadatos KRaft/topic
   IDs/offsets, junto con production de checkpoints. Nunca iniciar broker vacío
   y pegar checkpoints antiguos, ni desactivar failOnDataLoss.
6. Ejecutar el helper e2-volumes.py con la imagen API cargada, `--user 0`, red
   none, 128 MiB: montaje de volumen en `/dest`, transferencia readonly en
   `/transfer` y script readonly en `/tool.py`. Ejemplo de argumentos Python:
   `/tool.py restore kafka /transfer/kafka.tgz --sha256 <hash_del_manifest>`.
   Repetir con checkpoints/models/cache y sus volúmenes. Rechaza Kafka no vacío,
   production ya existente, rutas inseguras, hashes distintos y modelos
   existentes diferentes. Conserva UID/GID Linux para Kafka y Spark.
7. Copiar mongo-e2 al Mongo remoto y ejecutar e2-mongo-transfer.sh `restore`
   con una ruta nueva `/tmp/lifemap-e2-*`. **Solo colecciones E2 ausentes**;
   no utiliza --drop ni restaura reviews/businesses. Si existe una colección E2
   previa o hubo restauración parcial, detenerse e inspeccionar: no borrarla ni
   encadenar reintentos destructivos. Los snapshots no se aplican encima de un
   streaming Azure que ya haya avanzado. En actualizaciones posteriores se
   conserva el estado remoto y solo se promueve código compatible.
8. Establecer E2_ENABLED=1 y SHA correcto en `.env` remoto. Arrancar Kafka,
   comprobar topic reviews/3 particiones restauradas; después streaming con
   checkpoints existentes, modelo temporal y riesgo fijados. Comprobar lag y
   salud; mantener API E1 sirviendo mientras se prepara la candidata E2.
9. Autorizar integración fast-forward de la rama E2 en main y primer push E2.
   Actualizar el job privado existente a Jenkinsfile de main, pollSCM H/2 y
   DEPLOY_TARGET=azure, habilitarlo y ejecutar baseline. Ninguna llave SSH va a
   Jenkins; el checkout público no necesita PAT. Revalidar los diez servicios,
   credencial Kaggle existente (sin mostrar su valor) y todos los gates.
10. La promoción cambia Caddy a la candidata saludable en 127.0.0.1:5101,
    actualiza streaming si cambió su imagen, espera salud, actualiza API, prueba
    diez endpoints y vuelve a 5100. Guarda SHA y comprueba HTTPS/DNS existentes.
    NSG solo 80/443 públicos, 22 restringido; no abrir 5100/5101, Kafka/Mongo,
    Spark/Dask ni Jenkins. Caddy admin permanece en loopback.

No se puede demostrar GitHub→Jenkins automático sin el push autorizado. Después
del baseline, un cambio mínimo aprobado a main debe disparar pollSCM y mostrar
Git SHA = etiqueta OCI = /health. Repetir build fallido y comprobar que no
cambia la versión pública. Esa demostración y la disponibilidad móvil HTTPS
son pendientes reales de aceptación, no resultados ya realizados en Azure.

## Reversión

La transacción conserva imágenes anteriores. Si falla una prueba posterior a
la conmutación, mantiene candidata mientras restaura streaming/API anteriores
y vuelve Caddy a 5100 saludable y al SHA anterior. Si no puede recuperar 5100,
conserva candidata activa y reporta fallo; cleanup no la elimina. Nunca reescribe
offsets/checkpoints para ocultar un error ni restaura Mongo encima del estado
existente. En el bootstrap inicial, volver a API E1 y parar solo Kafka/streaming
si es necesario; preservar los volúmenes E2 nuevos para diagnóstico. Cualquier
restauración de emergencia de Mongo requiere revisión adicional, no --drop.
